# Agent 工程判断标准

## 背景

- 记录今天讨论后形成的共同标准：市面上很多 agent 能做出 demo 外观，但真正稳定的 agent 工程能力稀缺。
- 这条标准用于后续学习 `ai-agent-course-code`，以及迁移到电力建模 / TEAP Agent 时判断方案是否靠谱。

## 现象

- 现在很多 agent 项目能做到：
  - 有聊天界面。
  - 能接 tool calling / MCP / RAG。
  - 能演示“用户说话 -> 模型调用工具 -> 返回结果”。
- 但常见问题是：
  - 成功时像真的，失败时不可控。
  - 工具参数、权限、副作用、错误恢复没有工程边界。
  - 没有 trace / eval，失败后不知道错在意图识别、工具选择、参数、RAG 还是解释。

## 当前理解

我们的标准：

```text
Agent 的难点不是“做得像人”，而是“失败时不像随机人”。
```

成熟 agent 应该满足：

- 成功路径可解释。
- 失败原因可定位。
- 危险动作可拦截。
- 工具调用可追踪。
- 结果质量可评测。
- 业务规则由确定性代码、求解器、校验器或规则引擎托底。
- LLM 只承担适合它的不确定部分：理解人话、拆解意图、提出候选动作、解释结果、生成草案。

不成熟 agent 的典型信号：

- 靠 prompt 堆规则，缺少代码校验。
- 工具名和工具职责模糊，例如 `do_task`、`handle_request`、`analyze_all`。
- 模型说调用什么就直接调用什么。
- 高风险工具没有确认机制。
- RAG 检索结果没有来源、没有裁剪、没有证据包。
- 没有 `toolCallId` / request trace / 运行日志。
- 没有回归样例，只靠手动问几句判断效果。

## 电力建模 Agent 标准

后续做电力建模 / TEAP Agent 时，优先追求稳定链路，而不是炫技式全自动：

```text
原始模型文件
-> Semantic IR
-> 确定性校验工具
-> 拓扑定位
-> RAG 证据包
-> LLM 解释
-> change set 草案
-> validateChangeSet
-> 用户确认
-> applyChangeSet
```

LLM 不应该直接做：

- 判断电力模型事实是否成立。
- 执行关键修改。
- 决定安全边界。
- 替代仿真器、优化器、校验器。

LLM 适合做：

- 理解用户意图。
- 选择候选工具。
- 整理规则和工具结果。
- 解释错误影响。
- 生成待验证的 change set 草案。
- 生成报告和用户确认摘要。

## 后续可能用途

- 用作 `ai-agent-course-code` 的学习验收标准。
- 用作 TEAP Agent 工具设计、RAG 设计、eval 设计的评审标准。
- 如果后续多次复用，可以升级到项目规范或专门 skill。
