## 我学到的机制

`tool-test/` 的主线是从“模型只能聊天”升级到“模型能请求外部工具做事”。

核心判断：

- 大模型不会直接执行工具，只会在回复里返回 `tool_calls`。
- Node.js 外层程序负责找到工具并执行真实函数。
- `ToolMessage` 负责把工具结果回填给模型。
- `while (response.tool_calls?.length)` 负责持续处理“模型请求工具 -> 执行工具 -> 回填结果 -> 再问模型”的循环。
- MCP 不是替代 tool，而是把外部工具标准化接入 agent 的协议层。
- 业务函数改造成 tool 时，重点不是简单包一层，而是设计 `name`、`description`、`schema`、稳定返回结构和副作用边界。

## 调用链

普通 LangChain tool：

```text
用户问题
-> modelWithTools.invoke(messages)
-> 模型返回 response.tool_calls
-> Node.js 找到对应 tool
-> tool.invoke(toolCall.args)
-> messages.push(new ToolMessage(...))
-> 再次调用模型
-> 模型输出最终回答
```

MCP tool：

```text
MCP server 注册工具
-> MCP client 连接 server
-> mcpClient.getTools()
-> model.bindTools(tools)
-> 模型返回 tool_calls
-> adapter 调 MCP server 执行工具
-> 工具结果回填给模型
```

## 关键坑

- 不要以为模型执行了工具；模型只提出工具调用请求。
- 不要把业务函数随便暴露给模型；tool 要有清晰职责和边界。
- 不要把 `execute_command` 这类高权限工具无约束交给模型；真实项目要加目录、命令、确认和审计边界。
- 不要把 MCP 理解成更高级模型能力；它是工具接入协议，最后仍然会变成模型可调用的 tools。

## 迁移到 TEAP Agent

TEAP Agent 的工具候选不应该是 `do_teap_task` 这类万能工具，而应该拆成清晰能力：

- `validate_teap_model`：只读校验模型完整性。
- `locate_issue`：根据错误定位拓扑位置。
- `project_topology`：投影出模型拓扑摘要。
- `explain_issue`：解释错误影响。
- `create_change_set`：生成变更集草案。
- `validate_change_set`：校验变更集是否安全。

当前结论：

```text
判断和解释可以交给 LLM。
确定性校验、定位、变更集生成和权限边界必须写成代码或工具。
```
